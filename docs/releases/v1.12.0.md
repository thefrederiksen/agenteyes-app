# AgentEyes v1.12.0 - release notes

Prepared 16 November 2026 for issue #193. The previous release is v1.11.11 (11 October 2026).

This release ships with known defects, on purpose. Having it is better than not having it.
The list of defects below is the most important part of this document. If something goes
wrong after you install this, look there first. Each entry says what you will see, which
platforms it affects, and its issue number.

---

## 1. What this release is on each platform

Only the Windows build comes out of the release pipeline. Linux and macOS are built from source.

| Platform | What you get | How it is built | Signed? |
|----------|--------------|-----------------|---------|
| Windows | Installer, CLI, setup CLI and the app as downloadable exes, plus an ffmpeg zip and `release-manifest.json` | `release.yml`, triggered by the `v1.12.0` tag | **No.** Code signing is switched off until the repository's signing variable is set, so the exes are unsigned. SmartScreen will show "Unknown publisher" (docs/signing.md). |
| Linux | **Nothing to download.** Build and install from a checkout of the `v1.12.0` tag | `scripts/linux/install.sh` on your own machine | Not applicable |
| macOS | **Nothing to download.** Build and install from a checkout of the `v1.12.0` tag | `scripts/mac/install.sh` on your own Mac | **Ad-hoc signed only.** No Apple developer identity (see below) |

`release.yml` runs only on a Windows runner and publishes no Linux or macOS assets. "Released on
three platforms" means the code is released on all three. A person on Linux or macOS has nothing
to download. Fixing that is #194, which is not part of this release.

**Windows still ships the existing Windows app.** The new cross-platform desktop app (#116) builds
and opens on Windows from source, but the installer installs the existing WPF app
(`AgentEyesApp-win-x64.exe`, built from `src/AgentEyes.App`). Moving the Windows installer over to
the new app is #160, which is still open.

**The GitHub release page will not show these notes on its own.** `release.yml` publishes the release
with a fixed one-line body ("Download AgentEyes-Setup-win-x64.exe and run it."). To show these notes
there, edit the release after the workflow finishes:

    gh release edit v1.12.0 --repo thefrederiksen/agenteyes-app --notes-file docs/releases/v1.12.0.md

## 2. How to install

### Windows

Download and run the installer:
`https://github.com/thefrederiksen/agenteyes-app/releases/latest/download/AgentEyes-Setup-win-x64.exe`.
Or use the one-line terminal install in README.md, which also updates an existing install. The
install is per-user and needs no admin rights. Because the exes are unsigned, Windows SmartScreen
will warn about an unknown publisher, and you have to choose to run it anyway.

### Linux

From a checkout of the `v1.12.0` tag:

    scripts/linux/install.sh

You need the .NET 8 SDK (`sudo apt install -y dotnet-sdk-8.0`). If ffmpeg is missing, the script
installs it, asking for your permission through sudo or the desktop's permission window. The
script builds both the recorder and the desktop app. It installs the recorder as a systemd user
service and starts both, and the app also starts in the tray at login. Recordings go to
`~/Videos/AgentEyes/`. To update, check out the newer tag and run the script again.

### macOS

From a checkout of the `v1.12.0` tag:

    scripts/mac/install.sh

You need the .NET SDK and ffmpeg (`brew install ffmpeg`). The script stops and tells you if either
is missing. It installs the recorder as a launchd user agent (`com.agenteyes.recorder`) and then
builds and opens `~/Applications/AgentEyes.app`. Recordings go to `~/Movies/AgentEyes/`.

**Two things only you can do, and they are expected:**

1. **Approve Screen Recording yourself.** Open System Settings > Privacy and Security > Screen and
   System Audio Recording and switch on **"agenteyes"**, the recorder service. Do not switch on
   "AgentEyes", the app. The app needs no permission because the service makes every recording.
   If "agenteyes" is not in the list yet, run `agenteyes shot --screen 1 --out ~/Desktop` once to
   make macOS ask. Check it worked with `agenteyes screens` and `agenteyes record status`. The
   install script ends by printing these same steps.
2. **Accept that the app is from an unidentified developer.** `AgentEyes.app` is signed ad-hoc,
   with no Apple Developer ID, no hardened runtime and no notarisation. Built on your own Mac, it
   runs there (scripts/mac/build-app.sh). Downloaded or copied to any other Mac, Gatekeeper refuses
   it because it carries no developer identity. Developer ID signing and notarisation are #181.
   They wait on the Apple Developer Program enrolment, which starts on 17 November 2026.

For sound the Mac is playing (system audio), macOS needs a virtual audio device first:
`brew install blackhole-2ch`. The microphone works without one.

## 3. KNOWN DEFECTS - read this when something goes wrong

All ten are open. None is fixed in this release. "Measured" means a QA or developer seat saw it on
a real machine. "Not measured" means nobody has checked that case yet. It does not mean the case
is safe.

### All three platforms

- **#157 - Audio drifts ahead of the picture when the microphone drops samples.** When the machine
  is heavily loaded, or the input device delivers fewer samples than it should, the finished
  recording's audio runs early from the first dropped sample onward and stays early. The longer the
  recording, the worse it gets. Nothing reports it: every stage says `done`. Measured on Linux at
  load 32-43: a 104.6 s video with 98.99 s of audio, 5.6 s short and early. On macOS the same
  mechanism was inferred, from the capture timestamps and the sample count, on a virtual input that
  delivers about 78 percent of its samples. It was not heard in the file, which was silence. It has
  not been provoked on Windows. The raw
  capture is in sync. The post-processing (the two-pass mux from #136) closes the gaps. On a quiet
  machine with a normal microphone it has not happened: all three platforms passed their mic sync
  rows on 16 November because no samples were dropped. That does not retire this defect.

- **#159 - The status says "idle" before the recording file exists.** After you stop a recording,
  `/status` goes to `idle` at once, but `recording.mp4` is still being written. For a while only
  `recording.mp4.muxing.tmp` is on disk. The wait is about 2.3 percent of the take length: 0.5 s
  after a 32 s take, 13.7 s after a 10-minute take and 40.6 s after a 30-minute take. Any script
  or person that stops a recording and opens the file straight away can find it missing. This
  works in short tests and fails on long recordings. Measured on macOS. The deferred mux is shared
  recorder code, but it has not been measured separately on Windows or Linux. Until this is fixed,
  the only reliable "finished" signal is `PostProcessing.mux.State` in the recording's manifest.

- **#188 - At 1 frame per second, a healthy recording can be ended as "never started".** The
  encoder writes nothing until its start-up delay has passed, roughly its thread count plus 15
  frames. At 1 fps on a machine with many cores, that is longer than the 45-second start-up limit
  added in this release (#113), so the watchdog ends a working capture with a false reason. Measured
  on a 10-core Mac with a synthetic source and the encoder forced to 36 threads, standing in for a
  machine with about 24 logical cores: first bytes after 51.7 s. The watchdog kill follows from
  that, but it has not been observed on a real many-core machine. The same Mac at its own thread
  count stayed inside the limit at 30.8 s, and 2 fps was safe on both. This is reachable only through the CLI or
  the API (`--fps 1`). The app's presets offer 15 to 60 fps. The always-on mode defaults to 10 fps
  (`AlwaysOnOptions.cs`). Whether this defect or #184 reaches that mode has not been measured.
  **The same issue corrects a figure you may have been told.** A recording that is killed or
  crashes keeps everything up to its last fragment. It loses about one fragment plus the encoder's
  start-up delay, which is about 6 s at 5 fps and more at lower rates. A code comment in
  `FfmpegArgs.cs` says "at most two seconds", and that figure was never measured. A recording that
  dies in its first seconds has nothing on disk. That empty window was measured at 3-5 s at 30 fps
  (3.7 s on a 10-core Mac, 4-5 s on a 32-core Linux machine). It is about 7.7 s at 5 fps and about
  30 s at 1 fps.

### Windows

- **#149 - A recording with the camera turned on does not finish.** The camera records normally
  (323 frames in the measured take). Then post-processing crashes with an access violation
  (`0xC0000005`) and stalls on its retry, so the recording never completes. The camera is a preset
  option in the Windows app, so you can hit this from the UI. It was measured on the one Windows
  laptop with a camera, before the Windows microphone fix (#146) merged. It has not been
  re-measured since, so nobody knows yet whether #146 changed it. macOS and Linux have no camera
  in the test fleet, so camera recording there is untested.

- **#184 - At 5 frames per second, the microphone track ends about 4.5 s before the video.**
  Measured: 39.4 s of audio in a 44.0 s video. The file looks healthy: it decodes, the video is
  complete, and the duration reads 44 s. The last few seconds of speech are missing from the audio,
  or the video runs on past the audio. Which of the two it is has not been established. 30 fps on
  the same machine did not show it. 15 fps has not been measured, and neither have macOS and Linux.
  It is pre-existing, not caused by this release's changes. It is reachable through the CLI or the
  API (`--fps 5`). The app's presets start at 15 fps.

- **#166 - A recording cannot be finished cleanly if the recorder process has died, or if the
  headless recorder is stopped.** Windows has no "please finish your file" signal for a capture
  that another process left behind. When a recorder dies mid-recording, the clean-up on the next
  start kills the leftover capture outright, and its log says the recording "may not be
  recoverable". Separately, `agenteyes serve` (the headless recorder, which is not what the
  installer runs on Windows) ignores a plain `taskkill`, and `taskkill /F` lost the take when
  measured. This release adds fragmented capture (#113), which is designed to keep a killed
  capture playable up to its last fragment. Whether that now saves most of such a take on Windows
  has not been measured.

- **#187 on Windows applies only to the new cross-platform app built from source.** In that app,
  "Run at login" writes a Linux autostart file that Windows never reads. The Windows app the
  installer ships has its own setting ("Start when Windows starts" / "Run at login"), which uses the
  Windows Run registry key and is not affected.

### Linux

- **#165 - If the recorder service crashes or is killed, systemd kills the capture 2-4 s later,
  before it can finish its file.** The installed unit uses `KillMode=mixed`. When the service
  process dies, systemd SIGKILLs the capture's ffmpeg 2 to 4 seconds later. The same capture sent
  a polite stop finished a complete 142.5 s file. When measured, the killed capture was a plain
  MP4 with no index (`moov` atom) and could not be played. This release's fragmented capture
  (#113) is designed to leave such a file playable up to its last fragment, minus the tail
  described under #188. The issue's measurement predates #113, and the combination has not been
  re-measured. The issue names reboot and shutdown as the cases where this really reaches a user.
  Neither has been measured.

### macOS

- **#186 - Opening the app while it is already running in the menu bar does nothing.** The case
  is AgentEyes already running tray-only. Measured through `open`: no window, no new process,
  nothing in the log. The Dock, Finder and Spotlight go through the same Launch Services route and
  are expected to fail the same way, but they have not been tested separately. The app looks dead, but it is running.
  Starting the executable inside the bundle directly works:
  `~/Applications/AgentEyes.app/Contents/MacOS/AgentEyesDesktop`. That is how it was tested, and it
  correctly hands over to the running copy and shows the window. Linux and Windows pass this check.

- **#187 - "Run at login" ticks, but the app does not start at login.** The setting writes a Linux
  (XDG) autostart file, which macOS never reads, and the checkbox then shows ticked. Nothing
  registers with launchd and no error appears. The recorder service's own start-at-login is
  separate, installed by `install.sh`, and does work. So recording continues after a reboot. Only
  the app window does not come back.

- **#176 - The Screen Recording grant survives an ordinary update, but is fragile in one way.**
  Measured: macOS ties the grant for an ad-hoc-signed program to its code hash. The service
  ("agenteyes") gets its hash from the .NET launcher stub (apphost), which does not change when the
  C# changes. So reinstalling from a newer checkout keeps the grant. On 16 November the apphost
  rebuilt from main was byte-identical to the installed one, with the same hash before and after.
  The risk: if the apphost itself changes, because of a different .NET SDK or apphost pack or an
  assembly rename, macOS treats the service as a new program and the grant is gone. Nothing in the
  product reports a missing grant yet; making that visible is part of this issue. If recordings
  ever come out black or empty after an update, check Screen Recording for "agenteyes" first.
  `AgentEyes.app` changes identity on every release, but it holds no grant and needs none today.

### Other open work that is not a defect in what ships

- #194: no Linux or macOS download.
- #181: macOS signing and notarisation.
- #160: the Windows installer still ships the WPF app.
- Windows code signing: the repository variable is unset.

## 4. What is new since v1.11.11

In plain terms:

- **Windows: a microphone recording with default settings completes** (#146). On a
  microphone that records at 44.1 kHz, post-processing stalled or crashed, and no default-settings
  mic recording completed. The mic is now resampled to 48 kHz before the noise filter.
- **One desktop app for all three platforms** (#116). The Linux desktop app became
  `AgentEyes.DesktopApp`, which opens on Windows, macOS and Linux. On Windows it is source-only in
  this release (see section 1).
- **A double-clickable Mac app** (#118). `AgentEyes.app` is a self-contained bundle installed in
  `~/Applications` beside the recorder service. It is ad-hoc signed (see section 2).
- **A stalled capture now ends and says why** (#113). Before, a capture that died or froze left the
  status reading `recording` for hours. Now a capture that exits, never produces output, or stops
  growing for 45 s ends the recording, and the fault is named on `/status` and in the manifest.
  The capture is written as fragmented MP4, so a killed or frozen capture still plays up to its
  last fragment.
- **Another process can no longer finish or interfere with a recording that is still being made**
  (#156). A capture now holds a claim that other processes can see, so a repair pass, the CLI or a
  second host leaves a live recording alone. Leftover capture processes from a dead recorder are
  cleaned up at start (on Linux and macOS with a polite stop first; on Windows see #166).
- **The test suite can no longer kill a live recording** (#151). A failing test used to kill every
  ffmpeg started since it began, including a live recording's. It now kills only the processes it
  started itself.
- **Linux and macOS recorders** (#102, #104), a **Linux desktop app** (#107), and a long run of
  macOS, audio and mux fixes, all listed below.

## 6. What was verified before this release

The recorder rows of the three-machine QA report (#142) pass on all three platforms. All of them
were measured on main `b0e6ae8`, with each machine reinstalled from main first:

| Row | Windows | Linux | macOS |
|-----|---------|-------|-------|
| 4 - screen, no audio | PASS | PASS | PASS |
| 5 - screen + mic, audio within 1.5 s | PASS (0.487 / 0.683 s) | PASS (0.095 / 0.080 s) | PASS (0.614 / 0.670 s) |
| 6 - 10-minute recording completes and plays | PASS, with truncation control | PASS, with truncation control | PASS, with truncation control |

What those rows do **not** cover, as #142 states it: healthy takes only, with no fault injected and
no second process tested. No samples were dropped, so #157 was not exercised. Frame rates other
than 30 were not tested (#184, #188). Acoustic speech capture is unverified on every platform. The
app rows found #186 and #187 on macOS.
