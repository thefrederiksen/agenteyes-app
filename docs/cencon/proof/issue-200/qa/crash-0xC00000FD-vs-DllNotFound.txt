The end-to-end crash in the developer's run 3 (repro/run3-forward-slash-root.txt): 1026 DllNotFoundException at
SetWindowLongPtrWndProc -> 1000 0xe0434352 -> 1000 0xc000041d, KERNELBASE offset 0xc569a. Cases C and E match it

RESOLUTION: two DIFFERENT failures share the forward-slash trigger, split by whether the extraction dir's parent
exists.
 * Parent exists (the end-to-end case: the --root install had already created <root>\, so <root>\bundle's parent
   was there) -> the apphost extracts the native DLLs, then the runtime cannot load PresentationNative_cor3.dll
   from the mixed-slash path -> DllNotFoundException. Reproduced in isolation 2/2 (C, E), with and without
   CREATE_NO_WINDOW - so the launch flags are not the variable.
 * Parent missing (the developer's isolated experiment created a fresh iso-fs folder name) -> the process dies
   in NATIVE code (ntdll) with a stack overflow before anything is extracted and before the runtime starts -
   consistent with the apphost's recursive directory creation not terminating on a forward-slash path. 2/2 (B, D).
   That is NOT the end-to-end failure. The developer's isolated experiment reproduced this second failure and
   read it as confirmation; the attribution to the forward-slash variable was nevertheless right, and is now
   confirmed with a matching symptom.
NOT measured: the exact apphost frame that recurses (no native dump was taken). The inference "recursive
directory creation" rests on: native fault in ntdll, nothing extracted, depends only on the parent existing.

Relevance: the PR makes both unreachable under --root (root normalised by Path.GetFullPath; nothing launched).
Both remain reachable outside --root by a forward-slash AGENTEYES_ROOT (handoff "Not fixed"); the filing for that
should name BOTH symptoms, because the stack-overflow one is what a user-wide variable with a not-yet-created
parent would produce.
