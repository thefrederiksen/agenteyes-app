VERDICT: FAIL - acceptance criterion 6 is not met.

Eight of the nine acceptance criteria are verified with evidence. The design is a genuine advance on the twice-rejected one and the discriminator holds: the rejected "newest wins, drop the rest" design, re-implemented independently by QA, stays green on failure mode 1 and goes red on both criterion-2 tests. 5. THE DEFECT - criterion 6

Criterion 6, verbatim: "Test: a reload starting after a UI delete but before the directory is removed does not resurrect the deleted row."
Failure mode 6, verbatim: "A reload starting after the UI removal but before the directory is physically gone sees the still-present manifest and re-adds the row permanently."

The two tests shipped for criterion 6 do not cover that scenario:

  • AReloadThatStartedBeforeTheDirectoryWasRemoved_DoesNotResurrectTheDeletedRow (LibraryCoherenceTests.cs:443-455) calls BeginSnapshot() before Delete(...). That is the case failure mode 6 explicitly does not describe.
  • AReloadThatStartedAfterTheDelete_StillShowsARecordingWhoseDeletionFailed (LibraryCoherenceTests.cs:464-474) takes the criterion-6 scenario and asserts the row COMES BACK. It is the criterion inverted and shipped as intended behaviour, without the criterion being renegotiated with the Product Agent.

Reproduction (deterministic, one thread, no timing)

string one    = Recording("one_video",    "2026-08-01T10:00:00Z");
string doomed = Recording("doomed_video", "2026-08-02T10:00:00Z");
var lib = Loaded(one, doomed);

// The user deletes it. MainWindow.DeleteRecordings drops the row now and removes the FOLDER
// afterwards on a worker (MainWindow.xaml.cs:1779-1791) - a noticeable beat for a big mp4.
lib.Delete(new[] { lib.Find(doomed)! });

// In that gap the repair service finishes a stage and asks for a reload. The manifest is STILL
// on disk, because the recursive delete has not finished.
lib.ApplySnapshot(lib.BeginSnapshot(), Snapshot(one, doomed));

Expected: ["one_video"]
Actual:   ["doomed_video", "one_video"]

The app's own log, from the QA run, shows the resurrection in the product's vocabulary:

[LibraryCoherence] PruneTombstones: dropped 1 tombstone(s) below epoch (nothing in flight)
[LibraryCoherence] Delete: 1 recording(s), epoch=2, rows=1
[LibraryCoherence] BeginSnapshot: epoch=3, in flight=1, rows=1
[LibraryCoherence] ApplySnapshot: epoch=3, snapshot=2, added=1, updated=1, removed=0,
                   kept live=0, refused resurrection=0, rows=2      <-- added=1 is the deleted row

Why it happens - two compounding causes

  1. The merge rule alone cannot cover it. The tombstone wins only when fact.Epoch > epoch. A reload begun after the delete has a HIGHER epoch, so it is treated as newer evidence - but it is not: the disk has not caught up yet, because the physical deletion is still running.
  2. The tombstone is pruned too eagerly. PruneTombstones sets horizon = long.MaxValue when nothing is in flight, so a delete performed with no reload running has its tombstone dropped in the same call that created it. After that the model holds no record of the deletion whatsoever.

Is it reachable in the shipped app?

Yes. DeleteRecordings hands the recursive folder delete to a worker (MainWindow.xaml.cs:1779-1791) and a multi-gigabyte recording folder takes real time. Inside that window a reload is triggered by any of the three RepairService stages (ResumeAsync/TitleAsync/ThumbsAsync all raise LibraryChanged, and the service runs on a timer, RepairService.cs:116), or by an import. The user then watches a recording they just deleted reappear, and it stays until some later reload happens to run after the folder is finally gone.

What a fix looks like (not prescriptive)

The deletion's OUTCOME is already known to the caller: DeleteRecordings runs the Directory.Delete loop and records which ones failed. Bounding the tombstone on that - hold it until the deletion settles, then drop it (success: the disk now agrees; failure: the row is allowed back) - satisfies criterion 6 AND keeps the "a genuinely failed deletion must reappear" property the second shipped test is protecting. An epoch-only bound cannot distinguish "the delete is still running" from "the delete failed", which is why it gets one of them wrong.

6. Guard-strength findings (not criterion failures)

6a. The runtime gate is castable-around

LibraryCoherence.Rows is typed ObservableCollection<RecentItem>, but the runtime type is RecentItemCollection and both types are internal to AgentEyes.App. Any type in that assembly can therefore write:

var rows = (RecentItemCollection)library.Rows;
using (rows.BeginCoherentUpdate()) rows.RemoveAt(0);   // accepted; the model is never told

Neither guard sees it: the IL scan only reports methods that NAME a _rows field (the developer states this limit honestly), and the runtime gate is satisfied because a scope is open. The model's fact table then disagrees with the rows, and QA reproduced the consequence (N9): the next ApplySnapshot throws the divergence InvalidOperationException, which in LoadRecent is outside any try and would be unhandled on the UI thread. "Unspellable-around" therefore overstates it by one step. Worth closing (e.g. keep BeginCoherentUpdate unreachable from outside the model, or exercise the divergence detection somewhere that cannot crash the window) but no product code does this today.

6b. "In exactly one place" measures methods, not subscriptions

TheWindowSubscribesToLibraryChanged_InExactlyOnePlace distincts the call sites by METHOD, so QA added a second _repair.LibraryChanged += ... inside MainWindow::.ctor and the whole guard set stayed green (30/30). Not a coherence defect - both subscriptions go through the model - but the guard does not prove what its name claims.

6c. Renamed route - the fail-closed arm holds

QA renamed DeleteRecordings to RemoveRecordings; EveryLibraryRoute_GoesThroughTheCoherenceModel failed with "is not in AgentEyesApp.dll, so this enumeration is checking a route that no longer exists". Verified, not taken on trust.

7. Thread affinity

LibraryCoherence captures Environment.CurrentManagedThreadId at construction and every public route calls RequireOwningThread (LibraryCoherence.cs:417-427); RecentItemCollection does the same on every mutation and on opening/closing a scope. The instance is a field initializer on MainWindow, so the owning thread is the UI thread. Every call site is on the dispatcher: the constructor, the Dispatcher.BeginInvoke in the RepairService callback, the Dispatcher.Invoke in Saved, the Processing callback's Dispatcher.BeginInvoke, and UI event handlers. QA re-ran the off-thread demonstration (nine routes, each observed to throw) and saw no thread exception in the real-app run. Verified.

10. Conclusion

NOT VERIFIED - 8 of 9 acceptance criteria met; criterion 6 fails.

This is a good change and the model is the right shape - the per-recording granularity genuinely answers what defeated the previous attempt, and the discriminator proves the test suite can tell the two apart. The one criterion that fails is a bounded, well-understood problem with an obvious fix in the code that already exists: the delete path knows whether the deletion succeeded, and the tombstone should be bounded on that rather than on an epoch. Criterion 6 also needs a test that actually constructs the interleaving the criterion names.
