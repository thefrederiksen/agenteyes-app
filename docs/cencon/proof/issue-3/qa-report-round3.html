The round-2 blocker is fixed and, more importantly, fixed as a CATEGORY rather than as a patch. I planted row writes in seven places the developer's decoys do not name - a new type, a local function, an async state machine, a delegate, a struct, a different property, and the rename: callback re-wired to the row - and the guard reported every one of them at its true home. Thirteen new interleavings all hold, nothing from rounds 1 and 2 regressed, and the real app shows 44 of 44.

ONE FINDING THAT IS NOT AN ACCEPTANCE CRITERION, AND THE INDEPENDENT GATE SHOULD SEE IT FIRST: the new stale-build check does not close the hole it was added for.

It compares source timestamps against the exe. That catches a restore that touches the file, but NOT a restore that preserves the original timestamp - Copy-Item, cp -p, robocopy, an archive extract. In that case the restored source is OLDER than the exe, so the check passes AND dotnet build itself skips recompiling, leaving the mutated binary in place while both the script and the gate report success. I reproduced this end to end and confirmed it by file hash. Section 5. It does not affect this verdict - my own runs were all made with --no-incremental and hash-verified - but it means the safety net added after the round-3 incident does not yet catch that incident's most likely form.

It is a category guard. It keys on the CALLEE - any RecentItem property setter - and reads every method in the assembly, so the container's kind, the method's shape, the compiler's rewriting and the property chosen are all irrelevant; moving the write relocates the report rather than escaping it. C7 confirms the developer's R10 claim exactly as stated, and three separate guards fire on it rather than one. The only ways past it remain the two the developer names: reflection, and a writable public field (of which there are none - section 2).

On S3b, stated rather than buried. Two renames of the same row can land in the opposite order to the order they were typed, and the model stamps whichever lands last - so the earlier-typed name can end up on screen. This is NOT a coherence defect and NOT a regression: the manifest write has exactly the same race and is the authority, so the next reload converges on whatever the manifest ended up holding. It affects which name shows until then. Recorded because it is the kind of thing that looks like a coherence bug when someone hits it.

5. The stale-build check (item 3) - it does not close the hole it was added for

I broke it four ways, as asked.

CaseExpectedActual
Source newer than exe (a real edit)refuse refuses, with the exact message
Exe newer than source (a legitimate run)allow allows, and prints build: ... (newest source: ...)
Touched-but-unchanged filerefuse (fail closed), and clear after one rebuild refuses; the exe timestamp does update on rebuild, so it clears
Partial rebuild - a Core-only change, then a full solution build allow (no false positive) the App apphost IS relinked, so no false positive
No-op rebuild, twiceallowno false positive
Restore that PRESERVES the original timestamprefuse ALLOWS - and the run proceeded to launch the app against the mutated binary

The hole, reproduced end to end

1. mutate LibraryCoherence.cs, then build     -> exe 18:30:45 carries the mutation
2. restore the file with Copy-Item from a backup
   (Copy-Item PRESERVES LastWriteTime, so the
    restored file is dated 18:30:15 - OLDER than the exe)
3. the check:  newest source 18:30:15  <  exe 18:30:45   -> NOT STALE
   library-proof.ps1 printed "build: ..." and launched the app.

4. dotnet build AgentEyes.sln -c Release
     "Build succeeded."   "AgentEyes.App -> ...AgentEyesApp.dll"
     dll timestamp AFTER the build: 18:30:45   (UNCHANGED)

5. dll hash before a forced rebuild: 633A9443...
   dotnet build --no-incremental
   dll hash after:                   7BBAF200...      -> DIFFERENT

So in this form the mutated binary survives both the new check AND a normal dotnet build: MSBuild's up-to-date check is also timestamp-based, sees inputs older than outputs, and skips compiling while still printing "Build succeeded". Only --no-incremental (or a clean) actually recompiles. That is the same false green the check was written to prevent, reachable by the most ordinary way to restore a backup on Windows.

What it does close, and what would close the rest

It genuinely closes the form where the restore touches the file - git restore, git checkout --, GNU cp without -p, an editor write - and that is a real improvement over nothing. What it cannot do is decide freshness from timestamps when the restore controls the timestamp. Content is the only reliable input: hash every src/**/*.cs and *.xaml, stamp that hash into the build output, and have the proof script compare - or, far cheaper, have the script simply run dotnet build -c Release --no-incremental itself as its first step and stop treating the build as somebody else's responsibility.

How I kept my own verification sound. Every mutation this round was built with --no-incremental, the restored-state build was hash-compared against the mutated one to prove it actually changed, and the final gate and the app run were both made from a --no-incremental build on a clean tree. The app run also shows the ApplySnapshot epoch=1, snapshot=44 line present - the very line whose absence was the only clue in the invalid runs.

9. Conclusion, and what the independent gate should look at

VERIFIED - all nine acceptance criteria met.

Three rounds, two blockers, and both were real: a delete bounded by an epoch that could not express "the disk has not caught up", and a rename route nobody had enumerated. Both are fixed at the level of the mechanism rather than the symptom, and in each case the developer generalised past the specific finding - the outcome-bound deletion, and a row-write guard that turned out to catch seven placements I invented rather than the one I reported.

For the gate, in priority order:

  1. The stale-build check (section 5) - the only open item. Not an acceptance criterion, so it did not block, but it is the safety net added after two invalid proof runs and it does not catch the timestamp-preserving form. It also means a plain dotnet build can report success without recompiling, so the gate's own numbers are only as fresh as the restore method that preceded them.
  2. S3b - two renames of the same row can land out of typed order. Not a coherence defect; the manifest is the authority and the next reload converges.
  3. The two stated limits of the row guard - reflection, and a writable public field. There are none today; the guard silently weakens the day someone adds one.
  4. The unsettled-deletion cost (round 2, section 6) - now structurally unconditional via Ui.RunThenPost's finally, which was the fix I asked for.
