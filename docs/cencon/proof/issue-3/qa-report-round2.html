5. THE DEFECT - a rename route outside the model (criterion 8, and criterion 4 on that route)

An IL scan of the whole app for writes to any RecentItem property:

TOTAL RecentItem property writes in AgentEyesApp.dll: 52
WRITERS OUTSIDE RecentItem and LibraryCoherence:       1

  AgentEyes.App.RecordingDetailWindow::CommitRename
      -> AgentEyes.App.RecentItem::set_Title

The code (RecordingDetailWindow.cs:214-230):

private async void CommitRename()
{
    string name = _title.Text.Trim();
    if (name.Length == 0 || name == _item.Title) return;
    ...
    await Task.Run(() => ManifestStore.Update(_item.Dir, m => m.DisplayName = name));
    _item.Title = name;        // <-- straight onto the live Library row; no epoch claimed
    ...
}

_item IS the live row: Details_Click -> ItemFrom(sender) (the card's DataContext, MainWindow.xaml.cs:1708-1709) -> OpenDetail (MainWindow.xaml.cs:1539). The dialog's title TextBox commits on Enter or lost focus (RecordingDetailWindow.cs:59-60), and the route is on the Library card's context menu (MainWindow.xaml: <MenuItem Header="Details..." Click="Details_Click"/>).

Reproduction

var lib = Loaded(dir);

long inFlight = lib.BeginSnapshot();     // its worker has already read the OLD manifest
lib.Find(dir)!.Title = "The new name";   // exactly what CommitRename does
lib.ApplySnapshot(inFlight, Snapshot(dir));

Expected (criterion 4): "The new name"
Actual:                 "Monitor 0"

The same construction through LibraryCoherence.Rename (R12a) keeps the new name. The difference is entirely the route.

Reachable in the shipped app

Yes. The reload's disk read is slow by design - the real-app run below shows one snapshot taking 420 ms over 44 recordings, and the repair service fires LibraryChanged from three stages on a timer. A modal WPF dialog runs a nested dispatcher frame, so the Dispatcher.BeginInvoke that carries LoadRecent executes while the Details dialog is open. If the snapshot's worker read that recording's manifest before ManifestStore.Update flushed it - which is the whole reason the write is awaited off the UI thread - the landing snapshot carries the old name and AdoptFrom writes it back over the user's rename. That is failure mode 4 word for word: "a still-current snapshot can overwrite a completed rename".

Why this is a criterion-8 failure and not a footnote

The issue's scope says: "One coherence model for every route that reads or mutates the Library: initial load, search, screenshot insert, saved-recording insert, import, packaging refresh, rename, delete, and every RepairService trigger. Enumerate them and prove none bypasses it." There are two rename routes. One is enumerated and owned; the other is neither. The enumeration is provably incomplete, and the scan that finds it is twenty lines - the same technique already used for the _rows field. The guards as built protect the COLLECTION; nothing yet protects the ROWS, and the rows are where a rename lives.

Suggested fix (not prescriptive)

The dialog is already given behaviour it cannot own, as callbacks: new RecordingDetailWindow(item, _cfg, rebuildWalkthrough: ..., delete: ...). A rename: callback that calls _library.Rename(item, name) fits the existing shape exactly. A guard in the same spirit as the _rows scan - "no method outside RecentItem and LibraryCoherence writes a RecentItem property" - would keep the third route from appearing later; it is currently a clean 52/51/1 split, so the guard would go green the moment this one is fixed.

6. The never-settled risk, answered honestly (item 1)

The cost is real and the developer states it accurately. A directory marked Removing outranks every snapshot at any epoch and is never pruned, so if CompleteDelete is never called that recording is invisible for the life of the process. QA confirmed it survives 25 reloads (R7a). Closing the window does NOT reset it: the window is hidden rather than destroyed (App.xaml.cs:217-222, Closing cancels and hides), so the same LibraryCoherence and its fact table live for the whole process. "Until restart" means a process restart.

How reachable is it? QA traced every escape from the settle:

  • The per-directory Directory.Delete is individually try/caught (MainWindow.xaml.cs:1801-1810), so a locked, missing, in-use or access-denied folder cannot escape the loop. Verified at model level: partial failure (R6) and a delete of an already-gone recording (R11) both settle correctly.
  • Log.Error cannot throw - Log.Write swallows its own IO errors (AgentEyes.Core/Log.cs:25-38). This was the most plausible escape and it is closed.
  • The remaining escape is Ui.Post itself: Application.Current.Dispatcher throws if Application.Current is null, which happens only during process shutdown - at which point the in-memory state is discarded anyway.
  • An interruption between marking and settling (app killed, power loss) loses the whole fact table with the process, so a restart rebuilds from disk. No hiding.
  • A recording hidden by a DIFFERENT recording's failed delete is NOT reachable: one LibraryDeletion covers only the directories the user selected, and every one of them is settled by the same unconditional call.
  • There is an escape hatch even when it does happen: an Insert into that folder - a save or an import - clears the mark (R7b).

The gap that remains, and it is worth closing. The settle is not in a finally, and the worker is fire-and-forget (_ = Ui.Run(...), MainWindow.xaml.cs:1796), so anything that ever throws inside that lambda is swallowed silently and the recordings vanish with no diagnostic. The comment above it says the settle is "NOT optional and NOT conditional", but structurally it is conditional on reaching the last statement. Ui.RunThenPost already exists in this codebase for exactly this shape (work in a try, Post in a finally, Ui.cs:29-37) and was not used here. Today the path is guarded well enough that QA could not construct a reachable failure; the fix is a try/finally and it makes the claim in the comment true structurally rather than by inspection. Recorded as a hardening note, not as the reason for this verdict.
