Two findings for the owner

Finding 1 - a macOS post-recording mux hang, newly REACHABLE because of this fix, but not caused by it. Deserves its own issue.

Reproduced with plain ffmpeg, no AgentEyes process involved, on the raw.mp4 that run 2 left behind. The command is the one the untouched post-recording code builds:

ffmpeg -y -i raw.mp4 -filter_complex "[0:a]arnndn=m='.../bd.rnnn',speechnorm=e=4:p=0.95,volume=1[m];
                                      [m]alimiter=limit=0.95:level=false[a]"
       -map 0:v -c:v copy -map [a] -c:a aac -b:a 160k recording.mp4
  -> never terminates; output stops at 262192 bytes, no moov atom

Narrowed:
  arnndn alone        on the same input -> OK in <=10 s
  speechnorm alone    on the same input -> OK in <=10 s
  alimiter alone      on the same input -> OK in <=10 s
  the full chain, audio only, no video  -> HUNG  (so it is not the video copy)
  the full chain on a captured .wav     -> OK    (so it is not the audio content)

So the trigger is the chained filter graph over the AAC audio stream that the AVFoundation capture writes into raw.mp4 - that stream carries only 39 packets for 10.976 s. Why this report calls it out but does not call it a defect of #111: the mux path, the filter chain and AudioMixOptions are not in this PR's diff at all, it reproduces outside the application, and it is shared with Windows and Linux. Before this fix macOS never produced a raw.mp4, so nobody could reach it. It is a real macOS gap in "stop leaves a playable file" and it should be filed and fixed on its own terms, not folded into a ticket scoped to removing one argument.

Also observed in run 2: with the Yealink selected, /status reported MicLevel 0 for the whole recording while a CLI capture of that same device with the same sound playing gave -33.5 dB. In video mode the service opens a SECOND AvfStream on the device that ffmpeg already holds, purely to drive the meter. That is the developer's own flagged open question, and this run is evidence for it. Also its own issue.

Finding 2 - one Windows-visible message outside the issue's IN list was reworded. The developer disclosed it and invited a bounce; this report surfaces it rather than deciding it.

FfmpegRecorder.DiagnoseImmediateExit, Windows wording:
  before:  the microphone "X" may not match a DirectShow device.
  after:   the microphone "X" may not match any DirectShow input device.

The issue's Scope IN list names DeviceResolver.cs lines 55, 76, 81, 105, 123, 128 and nothing else, and all six of those are byte-identical on Windows (section AC6). This seventh message lives in FfmpegRecorder.cs. Against it: the issue's own problem statement calls this exact message out ("the error message blames the wrong platform"), it still says DirectShow on Windows so no Windows reader is misled, the article fix is needed because "a AVFoundation device" is not English, and the issue flags the wording scope as "the negotiable part of this issue". This report does not treat it as a criterion failure - the criterion's subject is the failed --mic match, which is unchanged - but it is the owner's call, not QA's, so it is stated here plainly rather than buried.

A broken instrument, caught

The first attempt to read the compiled Windows assembly used strings -a -el agenteyes.dll | grep -i DirectShow, which returned nothing. That looked like a clean result and was not one: macOS strings does not support -el, and a calibration search for a literal known to be in the file (agenteyes screens) also returned zero. The instrument was replaced with a UTF-16LE scan that finds that literal 8 times, and every assembly result in this report comes from the calibrated one. Recorded because an empty result is a broken instrument until proven otherwise.
