# Issue #161 - Windows derivation question: can a spoofed environment defeat the guard? Measured, 2026-11-16 ~17:03 local.
# Binary: agenteyes.exe built from PR #175 head 398581f (SDK 10.0.301 building net8.0, runtime 8.0.21), Windows 11
# Home 10.0.26200. The owner's service on 7882 was NOT asked: every run points AGENTEYES_SERVICE_PROBE_PORT at a free
# port of this seat's own, so the result is the DERIVATION half alone.
#
# ANSWER: YES, the PATH half of the guard is defeated on Windows by ONE variable, USERPROFILE. Windows is NOT
# correct by construction. .NET does resolve the folders through the shell's known-folder API (spoofing
# LOCALAPPDATA alone changes nothing), but the known-folder values are REG_EXPAND_SZ "%USERPROFILE%\AppData\Local"
# and "%USERPROFILE%\Videos" (User Shell Folders, quoted at the end), and they are expanded against THIS PROCESS's
# USERPROFILE. GetFolderPath(UserProfile) itself still returns the real profile, because it comes from the token.
# So under USERPROFILE=<scratch>\fakehome:
#   - RealLibrary.DeriveForThisProcess() names <scratch>\fakehome\AppData\Local and <scratch>\fakehome\Videos as
#     "the REAL" roots (PART A), so the guard's path rule ACCEPTS a redirect onto the owner's real local app
#     data and the owner's real Videos (PART A attacks 1 and 2: "guard's real roots: ACCEPTED").
#   - CONTROL: the counterfactual "a guard that reads %LOCALAPPDATA% / %USERPROFILE%\Videos" derives exactly the
#     same scratch paths and gives the same verdicts. Under this spoof the guard behaves exactly like a guard
#     that reads the environment.
# POSITIVE CONTROL (end of file): with NO spoof, the same harness and the same real binary REFUSE both attacks by the
# PATH rule ("overlaps the REAL state root" / "overlaps the REAL recordings root"), before any disk check. So the
# instrument can refuse, and the ACCEPTED verdicts above are caused by the spoof alone.
# What saved the real binary (PART B): the CONTENT rule (pass 3 F1). The real AgentEyes folders exist, are non-empty
# and carry no scratch marker, so both attacks were refused with exit 5, B1 on 'alwayson' and B2 on a recording
# folder name. B3 (both at scratch, same spoof) is ACCEPTED, so the refusals were not caused by the spoof itself.
# Consequence 1: on Windows, rule 2 (content) is the ONLY layer under a spoofed USERPROFILE. A real AgentEyes
#   folder that is empty or absent would be accepted, and the redirected process would then mark it and use it.
# Consequence 2: the refusal is reached by LISTING the owner's real state root and real recordings root, which is
#   a read of the real library. Reported at once to the lead. Verified read-only afterwards: the snapshots of both
#   real roots (names and creation times, depth 2) show 0 new entries, there is no .agenteyes-* file in either real
#   root or its parent, and the same query does find the marker in the scratch root (positive control).
# The comment in RealLibrary.cs ("Windows is unchanged: there the real folders come from the shell's known-folder
# lookup, not from a variable this process's environment sets") is FALSE as measured here.
