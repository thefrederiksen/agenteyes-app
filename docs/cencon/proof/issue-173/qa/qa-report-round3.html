D2 (blocking): the 80-column gate misses an 80-column PowerShell, the original tool

A tier-2 break (beside punctuation) is joined only if the line before it is at least 80 bytes long, padding included. The defect that started this issue tells us what width PowerShell actually writes:

main da85516: docs/cencon/proof/issue-156/qa-windows/run-rc-main.txt line 53
  119 content bytes (120 with the LF); no redaction falls inside it; ends  ...access the file 'C:\Us
  line 54 begins  ers\<name>\AppData\...           (the Remove-Item error, Windows PowerShell, 120-column console)

On a 120-column console, Windows PowerShell's formatter wraps at width - 1. pwsh 7.6.6 on this Mac does the same: Format-List with no console attached formats at 80 and writes lines of at most 79 columns. So an 80-column PowerShell writes 79-column lines, and a tier-2 break on one of them is never joined. 80 columns is not an edge case. It is the default for macOS Terminal, Linux terminals, an ssh pty, and pwsh with no console.

Is 80 the right threshold or a convenient one? Convenient. Nothing in the corpus pins it. With WRAP_WIDTH set to 79, 72, 60 or 40, all 50 corpus files still behave as declared, and the whole tree still has 0 hits (qa/qa-r3-mutations.txt). Every false positive that needs the gate has a short line before the break, under 40 columns. So 80 blocks nothing measured, and it lets through a width the original tool really produces. The declaration in declared-miss/ and the docstring also understate the miss: they say "narrower than 80", but an 80-column PowerShell is missed too.

Fix: set the gate to 79 or lower, with the reason in the docstring (PowerShell writes width - 1). Add red corpus files at 79 columns (after the prefix, inside the prefix, before the at-sign). Add at least one green file whose line length sits just under the chosen gate, so the number is pinned from both sides.

D3 (blocking): an indented split right at the separator is missed, and the docstring says it is caught

The docstring says: "A home path split after its prefix is still caught as written, because the partial name is itself a name". That is true when the split leaves at least one name character on the first line. It is false when the split falls exactly on the separator: the first line ends in C:\Us+ers\ with no name, and the indented next line starts with the name. Neither line holds a match.

PowerShell Format-List writes exactly this shape. pwsh 7.6.6 here, [pscustomobject]@{Message="... C:\Us+ers\planted-probe\..."} | Format-List, breaks a long value mid-path and continues at column 10:

Message : Cannot remove item because it is being used by another process at
          the long location C:\Us+ers\planted-probe\AppData\Local\AgentEyes\reco
          rdings\2026-11-17\x.mp4

Probe L-formatlist-indented-split-at-separator is GREEN (missed). miss03 (a split inside the prefix) is the same mechanism, and it is a plausible real leak for the same reason. Format-List of an error or exception object, with a path inside its message, is an ordinary thing for an agent to dump into evidence.

Fix: either catch it (for example, join an indented continuation when the line before it ends at a bare home prefix or mid-prefix, and the indent matches a Label : value column), or correct the docstring and pin this exact shape in declared-miss/ with the Format-List reason. Correcting the docstring alone is acceptable only if the lead accepts the Format-List gap.
