3. The design decision, judged

The handoff says the per-user systemd unit decided it: "A .deb is installed by dpkg as root ... it would have to ship the unit to /usr/lib/systemd/user, enable it globally for every account". That load-bearing sentence is false, and QA measured it. In the same container (systemd 255), as root, a unit shipped to /usr/lib/systemd/user was enabled and started for ONE account with systemctl --user --machine=qauser@.host enable --now. The result was enabled/active for that user, systemctl --global is-enabled stayed disabled, and a second account got no link. A .deb has a second option too: ship the unit disabled and let the user, or the app's first run, enable it. That needs no maintainer-script trick at all.

The conclusion still holds, for reasons the handoff touches but does not lead with: (a) a postinst does not reliably know WHICH user to enable for. $SUDO_USER is absent under PackageKit or a software centre, and --machine=user@ needs that user's manager running. (b) dpkg owns system paths, so the product would move out of ~/.local/lib, the unit's ExecStart=%h/.local/lib/... would change, and every update would need root. Today only the one-time ffmpeg and libvlc installs do. (c) The tarball reuses the exact install.sh every fleet machine already runs. A .deb is a viable alternative with different trade-offs, not an impossibility. The false sentence lives only in the handoff and the issue comment. The README's claim, "installs, for you alone", is accurate.

4. The dry-run trigger: what actually prevents a publish

  • The publish step has if: github.event_name == 'push' && startsWith(github.ref, 'refs/tags/v'), and the only triggers are a v* tag push and workflow_dispatch. A dispatch has event_name == 'workflow_dispatch', so the step is skipped whatever ref is chosen, including a tag ref. It was skipped in 44052244930 and 44054835280. The dry-run upload is gated the opposite way.
  • If that guard were wrong, for example deleted: (1) a dispatch on a branch reaches gh release create <branch name> --verify-tag, which refuses because no tag of that name exists, so the step goes red and nothing is published. (2) A dispatch on a tag ref would publish that tag's release, and the tag-equals-version check would not protect it, because that check is also skipped on dispatch. If the tag already has a release, gh fails "already exists". The real exposure is therefore a future tag whose own tag-push run failed. Today's three tags with no release (v1.4.6, v1.4.7, v1.11.1) cannot be dispatched, because their workflow file has no workflow_dispatch.
  • Latent finding, inert today: permissions: contents: write and the signing step also apply to dispatch runs. The signing step's only gate is vars.SIGNING_CERT_PROFILE != '', and gh variable list is empty today. Once signing is configured, any dispatch of any branch would sign that unreviewed branch's exes with the company certificate and upload them as the release-dry-run artifact. Suggested follow-up: also gate signing on github.event_name == 'push'. This is not a defect of this PR's criteria.

5. The 1-in-10 Linux test failure

Not identified by name, and QA will not pretend otherwise. The developer's session log on this machine fixes the circumstances but not the name: at 09:02:13 the building dotnet test tests/AgentEyes.Tests.Linux ran in parallel with dotnet build tests/AgentEyes.Tests -p:EnableWindowsTargeting=true, 4 s after a GET /status to the live service, and the result was "Failed 1, Passed 472". The output was filtered to the summary line, so no test name exists anywhere.

QA ran 95 full-suite runs with 0 failures: 41 quiet, 20 under a rebuild loop, 24 as concurrent pairs, and 10 exact replays of the developer's pairing. The #174 mechanism was then shown live on this machine: HeadlessControlServerFramingTests.FreePort() binds port 0, reads the number, releases it, and the server binds it again later. With a bounded helper holding 4000 random loopback ports (about 14 percent of the ephemeral range), 15 runs of that class gave 5 failures in 4 runs, every one "Address already in use". A parallel build's NuGet restore opens outbound connections from the same ephemeral range, so #174 is the leading candidate. It is still a candidate, not a proven identity.
