Issue #28, Review Gate round 2 - mutation evidence.

Every new check in tests/AgentEyes.Tests/CameraFailurePathTests.cs was run against KNOWN-BAD
product code before being trusted. Each mutation below was applied, the 17 CameraFailurePathTests
were run, and the mutation was then reverted. A check that passes both before and after a fix
proves nothing; an all-passing run here would mean these checks are decorative.

The first two mutations are not paraphrases of the defect - they are the LITERAL merged code,
restored file-for-file from commit eee17b4 (`git show eee17b4:<file>`), which is the code the gate
rejected. The other four reinstate one merged decision each inside the rewritten recorder, because
that class was restructured behind ICameraProcess and cannot be restored wholesale.

  1 cli-boundary     Commands.cs restored from eee17b4 - the camera opened into a bare local with
                     no finally and no using anywhere on the path
  2 devices-fallback RestServer.cs restored from eee17b4 - a camera-enumeration failure caught and
                     answered as cameras=[] with HTTP 200
  3 probe-timeout    the open probe treats "has not failed yet" as opened
  4 probe-exitcode   the open probe rejects only a NON-ZERO exit, as the merged code did
  5 terminate        Stop ignores whether the process survived the kill, as the merged code did
  6 lost             Stop computes the mid-run loss into a local, logs it, and never assigns
                     _lostMidRun - the merged code exactly

Baseline, unmutated: Passed! - Failed: 0, Passed: 884, Skipped: 0, Total: 884 (whole solution).

================ MUTATION 6: lost (gate defect 4) ================
  Failed AgentEyes.Tests.CameraFailurePathTests.Stop_WhenTheCameraDiedWithoutItsExitCallbackDelivered_RecordsTheTrackAsLost [2 ms]
  Error Message:
   a camera that ended before the stop is a TRUNCATED track

Stop_WhenTheExitCallbackWasDelivered_StillRecordsTheTrackAsLost deliberately KEEPS PASSING under
this mutation, and that is correct rather than a gap: it guards the other route to the same fact
(the delivered callback), which the merged code did handle. The two together say the manifest is
right whether or not the callback arrived in time.


What this evidence does NOT cover, stated rather than implied:

  - It proves each check fires on the defect it was written for. It does not prove the checks would
    catch a DIFFERENT defect in the same code.
  - The behavioural checks (3-6) drive the real FfmpegCameraRecorder over a controlled process. They
    say nothing about ffmpeg itself: that a real webcam opens, records and is handed back is the
    running-app evidence in handoff.md, not this file.
  - The structural checks (1-2) see the failure BOUNDARY and the calls a finally handler makes. They
    cannot prove that handler is correct - only that the boundary exists and disposes the camera.
