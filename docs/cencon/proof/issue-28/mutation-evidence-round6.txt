D. WHAT THESE CHECKS CANNOT SEE - stated, not implied
===============================================================================================

  * They are driven through the ICameraProcess seam, the same route the Review Gate's probe used.
    They prove what FfmpegCameraRecorder concludes from a given sequence of ffmpeg behaviours. They
    prove nothing about ffmpeg itself; that a real webcam records is the running-app proof's job.

  * The exit-code clause treats a NEGATIVE exit code as an abnormal termination and a non-negative
    one as ffmpeg having run its own exit path. It therefore cannot see an ffmpeg that ran its exit
    path and still failed to write a usable trailer while reporting a positive code. That limit is
    deliberate: ffmpeg is not pinned to one build here (FfmpegLocator takes a bundled, PATH or
    winget ffmpeg) and different builds answer "q" with 0 and with 255, so reading every non-zero
    code as a broken take would turn AC17's positive control into "unknown" on another machine.

  * The CLI check (defect 5) is STRUCTURAL. It proves the transfer to a StrandedCameraOwner is
    compiled into Commands::Video, and that Video still disposes the recorder. It does not prove
    the transfer runs on every path through that method; the owner's own behaviour is what the
    StrandedCameraOwnerTests exercise.

  * A CLI process cannot outlive itself. RetainIfStranded keeps the reference for the rest of the
    command and routes the decision through the same method the service uses, and the PID is
    printed and logged - that printed PID is what stays actionable after agenteyes.exe exits. No
    claim is made that a finished process has something to come back to.
