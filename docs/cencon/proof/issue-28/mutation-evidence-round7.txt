== 2. THE TWO CLI FAILURE BOUNDARIES, ONE MUTATION EACH ============================

The gate's round-5 QA ruling: both transfers are present and correctly ordered in the
product, but the guard proved only that AT LEAST ONE owner call exists in Commands.Video,
so deleting either boundary alone stayed green.

Mutation A - delete the FAILED-OPEN transfer (Commands.cs:351-365): the whole
             `if (CliStrandedCameras.RetainIfStranded(cameraRec, dir)) { ... } else { ... }`
             in the camera-open catch, leaving only DiscardEmptyRecordingDirectory(dir).

Mutation B - delete the FINAL transfer (Commands.cs:511-518): the whole
             `if (CliStrandedCameras.RetainIfStranded(cameraRec, dir)) { ... }` in the
             method's finally.

Each mutation was applied to a clean round-6 tree, built, and the guard run; the tree was
reverted with `git checkout -- src tests` before the next one. Every run was gated on a
clean build first - a build failure with --no-build would have run the PREVIOUS binary and
produced a result about code that was never compiled.

Each deletion now fails on the assertion about ITS OWN boundary, not on a shared count. The
count assertion is still there, last, and says only that there is no third transfer.

How the two sites are told apart, since they are the same call to the same method: IL
exception regions. The failed-open transfer runs while the command's own finally is still
owed, so it is INSIDE a try covered by a Finally region; the final transfer IS that handler,
which no try region of its own covers. Both facts come from CompiledCode.GuardedCalls, which
throws if Commands::Video is missing or contains no call to the callee at all - so "found
nothing" can never read as a pass.
